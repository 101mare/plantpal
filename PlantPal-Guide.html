01 Was ist PlantPal?

Ein selbst-gehosteter, Pokédex-artiger Gieß-Tracker für deine Zimmerpflanzen. Jede Pflanze ist ein Eintrag in deinem „Plantdex“; die App weiß, wann welche Pflanze Wasser braucht, und erinnert dich per täglicher E-Mail. Mehrere Nutzer (invite-only), passwortloser Magic-Link-Login, Pixel-Art-Optik.

⏳

Thirsty-Mechanik

Pro Pflanze: last_watered_at + interval_days. Ist heute (Berlin-Zeit) ≥ letztes Gießen + Intervall, gilt sie als „thirsty“. Tages-Granularität, keine Uhrzeit-Pingeligkeit.

📷

Plantdex

Foto-Upload wird serverseitig auf 96×96 px verkleinert und per CSS image-rendering: pixelated als Pixel-Art angezeigt. Kein Limit an Pflanzen.

✉

E-Mail-Reminder

Täglicher Digest (Default 08:00 Berlin, pro Nutzer einstellbar) — aber nur, wenn es wirklich durstige Pflanzen gibt. Kein „nichts zu tun“-Spam.

🔑

Auth

Magic-Link oder 6-stelliger Code; Registrierung nur mit Invite-Token. Sessions gleiten bei Aktivität mit (alle ~24 h auf +90 Tage erneuert), hart gedeckelt auf 180 Tage ab Login. Läuft eine Session ab (90 Tage inaktiv oder 180-Tage-Hard-Cap) → 401 → Redirect auf /login → neuer Code/Link. Tokens nur als HMAC-Hash in der DB.

📊

Statistiken

Gieß-Historie, Streak (mit Gnaden-Tag), 30-Tage-Konsistenz, Ø-Intervall, Aufschlüsselung nach Räumen. Die Datenbasis, auf der die Gamification aufsetzt.

🌱

Maskottchen

„PlantPal“, eine kleine Pflanzen-Kreatur. Heute statisch — soll künftig animiert & interaktiv werden und der Träger der Gamification sein (Abschnitt 05).

Privacy-first

Alle Daten (Pflanzen, Bilder, Accounts) liegen auf deinem Server. Der einzige externe Pflicht-Dienst ist Resend für den Mailversand. Schriftarten, Icons und Hintergründe sind selbst gehostet — kein Google-CDN, kein Tracking.

02 Wie es funktioniert (Architektur)

PlantPal ist bewusst klein und „boring tech“: ein Python-Prozess, der gleichzeitig die JSON-API und die fertig gebaute React-App ausliefert, mit SQLite als Datenbank. Genau das macht es perfekt für einen Raspberry Pi.

Request-Fluss: Browser → Cloudflare (TLS) → Tunnel → ein FastAPI-Prozess → SQLite-Datei. Keine offenen Router-Ports.

Die Bausteine

Warum genau ein Prozess / ein Worker?

Das ist eine bewusste Design-Entscheidung mit Folgen fürs Hosting: SQLite mag genau einen schreibenden Prozess, und der APScheduler-Digest darf nur einmal laufen (sonst doppelte Mails). Also: ein uvicorn-Worker, der API, SPA und Cron in sich vereint. Das ist der Grund, warum du PlantPal nicht einfach auf 3 Replicas hochskalierst — merke dir das für den k3s-Teil (Abschnitt 04).

Sicherheit, die schon drinsteckt

Request-Härtung

Pure-ASGI-Middleware kappt zu große Bodies vor dem Puffern (413, OOM-Schutz beim Single-Worker), setzt strenge Security-Header (CSP same-origin, X-Frame-Options: DENY, HSTS in Prod), CSRF per Double-Submit + HMAC.

Rate-Limits & Fail-Fast

Login/Upload/Mutationen sind ratenbegrenzt; hinter dem Tunnel wird die echte Client-IP aus CF-Connecting-IP gelesen. validate_runtime() bricht beim Start ab, wenn Prod-Secrets/Domain unsicher sind.

Login & Re-Login — der Nutzer-Flow

Läuft die Session ab (90 Tage inaktiv oder 180-Tage-Hard-Cap), landest du nach dem 401 automatisch auf /login. So forderst du Zugang an — es ist kein reiner Ein-Klick, weil der Server wissen muss, wohin er Link/Code schickt:

1 · Anfordern /login

Bei PlantPal anmelden du@beispiel.de Login-Link senden → „Schau in dein Postfach – Link und Code sind unterwegs.“

E-Mail eintippen, Button klicken. Eine Mail enthält beides: einen klickbaren Magic-Link und einen 6-stelligen Code.

2 · Anmelden /login/code

Code eingeben du@beispiel.de • • • • • • Anmelden Code erneut senden

Magic-Link in der Mail anklicken = sofort drin (nichts tippen). Oder den Code hier eingeben. „Code erneut senden“ ist der echte Ein-Klick-Weg für einen frischen Code (E-Mail ist schon ausgefüllt).

Zwei Dinge, die im Code stecken

Rate-Limit: max. 3 Anforderungen/Stunde pro E-Mail (10/h pro IP) — „Code erneut senden“ lässt sich also nicht endlos drücken.   Anti-Enumeration: die UI zeigt immer „Schau in dein Postfach“, egal ob die Adresse einen Account hat (verrät keine Nutzer); die Antwortzeit ist auf ~350 ms geglättet.   Code-TTL 10 min, 5 Fehlversuche → verbrannt; Magic-Link single-use, 30 min.

03 Auf dem Raspberry Pi hosten

Die gute Nachricht zuerst: Das Repo ist bereits Pi-fertig. Es gibt ein Dockerfile, eine docker-compose.yml (App + Cloudflare Tunnel + optionales Litestream-Backup), einen Caddyfile als VPS-Alternative und ein Backup-Skript. Du musst es im Wesentlichen nur konfigurieren und starten.

Voraussetzungen

Hardware

Raspberry Pi 4 oder 5 (ein Pi 3 reicht knapp). 64-Bit Raspberry Pi OS (Bookworm) — das Image ist linux/arm64. Empfehlung: vom SSD/USB booten statt SD-Karte (SD-Karten sterben unter Dauer-Schreiblast).

Software & Konten

Docker + Compose-Plugin. Eine Domain (idealerweise beim Cloudflare-Registrar) + Cloudflare-Account für den Tunnel. Ein Resend-Account für den Mailversand.

Docker auf dem Pi installieren 
# offizielles Convenience-Skript (erkennt ARM automatisch)
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER     # danach neu einloggen
docker compose version            # Compose-Plugin prüfen

Die drei Container (docker-compose.yml)

Schritt für Schritt zum Live-Betrieb

  1. Cloudflare Tunnel anlegen

    Cloudflare-Dashboard → Zero Trust → Networks → Tunnels → Create. Public Hostname = deine Domain (z. B. getplantpal.com), Service = http://plantpal:8000. Das Tunnel-Token kopieren.

  2. Mail-Domain bei Resend verifizieren

    In Resend deine Domain als Absender hinzufügen und die SPF/DKIM/DMARC-Records in Cloudflare DNS setzen — sonst landen Magic-Links im Spam.

  3. Repo holen & .env ausfüllen

    git clone <dein-repo> plantpal && cd plantpal
cp .env.example .env

# Secrets erzeugen (zwei Mal ausführen, je einen Wert eintragen):
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
# -> TOKEN_PEPPER und CSRF_SECRET in .env
# Außerdem setzen: BASE_URL=https://getplantpal.com,
# RESEND_API_KEY, RESEND_FROM_EMAIL, CLOUDFLARE_TUNNEL_TOKEN

  4. Bauen & starten

    docker compose up -d --build   # baut SPA + Python-Image, startet plantpal + cloudflared
docker compose logs -f plantpal # Start & Migrationen beobachten

  5. Ersten Admin anlegen

    docker compose exec plantpal python -m plantpal.cli bootstrap-admin --email du@beispiel.de
# druckt einen Login-Link in die Konsole -> öffnen -> eingeloggt
# Freunde einladen: ... cli create-invite --created-by du@beispiel.de
Updates

Neue Version ausrollen ist ein Dreizeiler — Migrationen laufen automatisch: 

git pull
docker compose up -d --build
docker image prune -f   # alte Layer aufräumen

Backups — bevor du echte Daten hast

SD-Karten sterben

Eine SD-Karte (und auch SSDs) gehen irgendwann kaputt. Richte ein Backup ein, bevor du dir Mühe mit echten Pflanzen-Daten machst. Es gibt zwei eingebaute Wege:

A · Cron-Snapshot + rsync

scripts/backup.sh macht einen WAL-konsistenten Snapshot (via cli backup) und kopiert DB und Bilder heraus. In die Host-Crontab: 

30 3 * * *  PLANTPAL_BACKUP_DEST=/backup/plantpal \
  /opt/plantpal/scripts/backup.sh

B · Litestream (kontinuierlich)

Streamt jede Änderung off-site zu S3/Cloudflare R2:

# .env: LITESTREAM_REPLICA_URL=s3://bucket/plantpal
docker compose --profile backup up -d
# Restore:
docker compose run --rm litestream \
  restore -o /data/plantpal.db "$LITESTREAM_REPLICA_URL"

Monitoring

Setze einen kostenlosen UptimeRobot-Monitor auf https://getplantpal.com/api/health. Der Endpoint meldet status, db_ok und scheduler_running — du wirst also auch dann alarmiert, wenn der App-Prozess läuft, aber DB oder Cron tot sind.

ARM-Images: auf dem Pi bauen oder cross-bauen?

Der einfachste Weg ist docker compose up -d --build direkt auf dem Pi — dann entsteht automatisch ein arm64-Image. Das dauert auf einem Pi ein paar Minuten. Wenn du schneller auf einem stärkeren Rechner (amd64) bauen und das Ergebnis auf den Pi schieben willst, nutze buildx mit QEMU für ein Multi-Arch-Image:

Optional: Multi-Arch-Image vom Laptop aus bauen & pushen 
docker buildx create --use --name pp --platform linux/amd64,linux/arm64
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/<user>/plantpal:latest --push .
# Auf dem Pi zieht Docker automatisch die arm64-Variante.
VPS-Alternative

Kein Cloudflare? Auf einem VPS mit offenen Ports 80/443 ersetzt der beiliegende Caddyfile den Tunnel und holt automatisch ein Let's-Encrypt-Zertifikat (reverse_proxy plantpal:8000). Auf einem Heim-Pi ist der Tunnel aber klar besser: kein Port-Forwarding, deine Heim-IP bleibt verborgen.

04 Docker, Swarm oder k3s?

Drei Fragen in einer: (a) Soll ich überhaupt Docker nehmen? (b) Wäre k3s eine gute Übung für die Arbeit? (c) Und was ist mit Swarm? Kurzantwort vorweg:

Empfehlung

Produktiv: Docker Compose. Für eine App auf einem Pi ist docker compose up -d exakt das richtige Werkzeug — reproduzierbar, ARM-tauglich, schon eingerichtet. Nichts Komplexeres nötig.

Fürs Lernen: k3s parallel als Lab. Wenn du Kubernetes für die Arbeit lernen willst, ist ein Pi mit k3s ein hervorragendes, risikoarmes Übungsfeld — aber als zusätzliches Lernprojekt neben dem stabilen Compose-Betrieb, nicht als Ersatz.

Swarm: kannst du überspringen. Es ist im Wartungsmodus, und für eine einzelne App auf einem Knoten bringt es kaum etwas gegenüber Compose.

Die Entscheidungsmatrix

Kriterium Docker Compose Docker Swarm k3s (Kubernetes)
Aufwand / Lernkurvesehr geringgeringhoch (YAML, kubectl, Netzwerk, Storage)
Passt für 1 App auf 1 Piidealokay, aber OverkillOverkill (funktional)

Quellen zu Wartungsstatus & Eignung: siehe Abschnitt 06.

Warum Docker (Compose) hier richtig ist

  • Schon fertig: Dockerfile + Compose-Stack existieren und sind durchdacht (non-root, Healthcheck, tini, gebackene Volume-Rechte für den Pi).
  • Reproduzierbar: „Läuft auf meinem Rechner“ = „läuft auf dem Pi“, weil das Image identisch ist.
  • Ein-Befehl-Updates & -Rollbacks und saubere Trennung von App, Tunnel und Backup.

k3s als Übung für die Arbeit — ehrliche Einordnung

k3s ist vollwertiges, CNCF-zertifiziertes Kubernetes in einer einzigen ~70 MB-Binary; für Single-Node ersetzt es etcd durch eine eingebettete SQLite. Heißt: Alles, was du hier lernst — kubectl, Deployments, Services, Ingress, ConfigMaps/Secrets, PersistentVolumeClaims, Helm — ist 1:1 das, was im Job auf „großem“ Kubernetes läuft. Genau deshalb ist es als Lernvehikel so wertvoll, und Swarm eben nicht.

Pi-Vorbereitung für k3s

Drei Dinge sind auf dem Pi nötig, sonst startet k3s nicht sauber: cgroups in /boot/firmware/cmdline.txt aktivieren, Swap aus, und am besten von SSD booten (Kubernetes ist schreibintensiv — SD-Karten gehen daran kaputt). 

# 1) an cmdline.txt anhängen (eine Zeile!):
cgroup_memory=1 cgroup_enable=memory
# 2) Swap deaktivieren:
sudo dphys-swapfile swapoff && sudo systemctl disable dphys-swapfile
# 3) k3s installieren (Traefik drin lassen oder weglassen):
curl -sfL https://get.k3s.io | sh -
sudo k3s kubectl get nodes

So sähe PlantPal als Kubernetes-Manifest aus

Der Clou fürs Lernen: Weil PlantPal SQLite + Scheduler in einem Prozess hält, ist es ein 1-Replica-Deployment mit einem ReadWriteOnce-PVC — du kannst es nicht auf mehrere Pods skalieren (das würde die DB und die Mails zerschießen). Das ist eine sehr lehrreiche Einschränkung: Du siehst direkt, warum „stateful single-writer“ und Kubernetes-Autoscaling sich beißen.

plantpal-k8s.yaml (Lernbeispiel, gekürzt) 
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: plantpal-data }
spec:
  accessModes: ["ReadWriteOnce"]
  resources: { requests: { storage: 2Gi } }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: plantpal }
spec:
  replicas: 1            # NICHT erhöhen: SQLite + Scheduler = single-writer
  strategy: { type: Recreate }   # kein RollingUpdate auf 1 RWO-Volume
  selector: { matchLabels: { app: plantpal } }
  template:
    metadata: { labels: { app: plantpal } }
    spec:
      containers:
        - name: plantpal
          image: ghcr.io/<user>/plantpal:latest
          ports: [{ containerPort: 8000 }]
          envFrom: [{ secretRef: { name: plantpal-secrets } }]
          volumeMounts: [{ name: data, mountPath: /data }]
          readinessProbe:
            httpGet: { path: /api/health, port: 8000 }
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: plantpal-data }
---
apiVersion: v1
kind: Service
metadata: { name: plantpal }
spec:
  selector: { app: plantpal }
  ports: [{ port: 80, targetPort: 8000 }]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: plantpal }
spec:
  rules:
    - host: getplantpal.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: plantpal, port: { number: 80 } } }
# Secret aus deiner .env erzeugen und alles ausrollen:
kubectl create secret generic plantpal-secrets --from-env-file=.env
kubectl apply -f plantpal-k8s.yaml
kubectl get pods,svc,ingress
kubectl logs deploy/plantpal -f
Bester Lernpfad

Halte den Produktivbetrieb auf Compose (stabil, simpel) und stelle parallel k3s auf demselben oder einem zweiten Pi auf, um PlantPal dort als Deployment+Service+Ingress+PVC neu zu deployen. So bekommst du echte, übertragbare Kubernetes-Praxis, ohne deinen laufenden Dienst zu riskieren. Cloudflare Tunnel kann auch auf einen k3s-Service zeigen — oder du nutzt den eingebauten Traefik-Ingress.

05 Gamification-Konzept

Ausgearbeitet von fünf kreativen Consultants (Game-Design, Verhaltenswissenschaft, Maskottchen/Narrativ, Meta-Ökonomie und Reddit-/Wettbewerbs-Recherche). Das Ergebnis ist eine kohärente Vision — keine lose Ideensammlung.

Der Nordstern

„Neko Atsume trifft Finch — gebaut von jemandem, der Pflanzen wirklich am Leben halten will.“ Ein wachsendes Maskottchen, ein füllbarer Plantdex, ein Haushalt der kooperiert — ohne Streak-Schuld, ohne Paywall, ohne Spam.

Die eine Regel, an der jede Mechanik gemessen wird: Wer die App 3 Wochen nicht öffnet und zurückkommt, soll es leichter haben, wieder anzufangen — nicht bestraft werden, dass er weg war.

Was die Recherche zeigt (Reddit & Konkurrenz)

Die Recherche-Agentin hat Reddit/HN, App-Store-Reviews und Game-Design-Analysen ausgewertet. Klares Muster:

✓ Zieht langfristig

Tamagotchi-Effekt — emotionale Bindung an eine reagierende Kreatur (Finch). „Abundance over Scarcity“ — kein Timer, kein Fail-State (Neko Atsume, Pikmin Bloom). Sichtbarer Fortschritt als Selbstmotivator (Forest). Recovery-Mechaniken → 3× höhere Langzeit-Bindung.

✗ Vertreibt

Guilt-Streaks („Duo-Anxiety“) — der Streak wird zum Ziel, der Bruch zum App-Abbruch (Quelle). Paywall vor dem Aha-Moment (Planta: 71 % der Top-Apps sperren Kern-Features). Generische Spam-Notifications („your plant needs water“ — welche?). Feature-Overload, der die simple Frage „wann gießen?“ verschüttet.

Lücke, die PlantPal besetzen kann

Es gibt kein selbst-gehostetes Pflanzen-Tool mit Consumer-UX (der direkte Konkurrent HortusFox ist technisch unzugänglich, MySQL, die HN-Community wünscht sich explizit SQLite). Und: keine Pflanzen-App nutzt ein Companion-Maskottchen ohne Guilt-Loop, den Plantdex als Completionism-Reward (wie Pokémon/Neko Atsume), oder echte Haushalts-Kooperation. Genau das ist PlantPals Heimspiel.

Das Maskottchen: „Spross“

Spross ist kein Avatar des Users, sondern ein eigenes Wesen, das aus dem Akt des Hütens lebt. Geduldig-neugierig, warmherzig-lakonisch — er kommuniziert nie in Sätzen, sondern in Gesten und kurzen, leisen Wort-Schnipseln (1–3 Wörter in Pixel-Font, die still unter ihm erscheinen und nach ein paar Sekunden verblassen). Nie ein Popup. Nie ein Vorwurf.

Der emotionale Kern

Spross ist ein Spiegel, kein Richter. Sein Aussehen spiegelt den Zustand deiner Sammlung: grüner Daumen → goldener, strahlender Spross; vernachlässigt → blasser, müder Spross. Das ist kein Urteil, sondern ehrliche Konsequenz — und damit der popup-freie Ambient-Nudge schlechthin. Wer Spross strahlen sehen will, gießt.

Zwei Fortschritts-Achsen (sauber getrennt)

Vitalität (VP) → Evolution

Nicht ausgebbar. Treibt Spross' Evolutionsstufe. Pflege schlägt Sammeln mind. 3:1 — pünktliches Gießen + Streak-Multiplikator dominieren, neue Einträge geben nur einen kleinen Einmal-Bonus. So lohnt sich Pflege, nicht Horten.

Tau → Kosmetik-Währung

Verdienbar durch Pflege, nie kaufbar, mit Tages-Cap (Anti-Grind). Kauft nur Kosmetik (Skins, Töpfe, Wallpaper). Inhaltliche Unlocks (Stats, Regal, Chronik) sind verdient, nicht erkauft — niemand „kauft“ sich vorbei.

Vitalitäts-Formel (Pflege dominiert) 
VP_pro_Tag = (Σ Gieß-VP aller Pflanzen) × Streak-Multiplikator + Einmal-VP

Gieß-VP/Pflanze:  pünktlich (±1 Tag) +10 · 2 Tage spät +5 · 3 Tage +2 · sonst 0
Streak-Mult.:     1–6 Tg ×1.0 · 7–13 ×1.25 · 14–29 ×1.5 · 30–59 ×1.75 · 60+ ×2.0
Einmal-VP:        neue Pflanze +15 · vollständiges Profil +10 · 100 Tg am Leben +50

# Beispiel: 8 Pflanzen pünktlich, 18-Tage-Streak = 8×10 ×1.5 = 120 VP/Tag
# Reiner Sammler (20 Pflanzen, alle überfällig) = ~400 VP gesamt → bleibt Stufe 2

Evolutionsstufen

Sechs Stufen, rein visuell ablesbar — kein Level-Zähler nötig. Der Aufstieg ist ein stiller 2-Sekunden-„Bloom“ beim nächsten App-Öffnen, danach ist das neue Idle- Verhalten einfach da. Der User entdeckt es.

🌱

1 · Keimling

Samenkorn mit zwei Keimblättchen, große Babyaugen. Schläft fast, blinzelt selten. Start.

🌿

2 · Sprossling

Steht erstmals auf einem Stämmchen, Blatt-Ärmchen, Antennen-Blatt. ~100 VP.

☘

3 · Blattgeist

Rund & warm, 4 Blätter, erste Wurzelranke am Boden. ~300 VP · 60 % Konsistenz.

🌼

4 · Rankenweiser

Beinchen, Blatt-Finger, kleines Blütenkrönchen, zarte Gold-Aura. ~700 VP · 75 %.

🌺

5 · Blütenwächter

Blatt-„Flügel“, volle Blüte, Wurzelfüße, sanfter Glow. ~1500 VP · 85 % · 30-Tg-Streak.

🌳

6 · Urgeist

Halb Wesen, halb Baum: Ranken-Arme, weise geschlossene Augen, kleines Ökosystem im Haar. ~3000+ VP · 90 % · 100-Tg-Streak.

Endlos-Tiefe statt End-Zustand: jede Pflanze sammelt eigene stille Alters-Marker (30/100/365 Tage), Räume verdienen Badges, und ab Stufe 6 gibt es ein optionales Prestige („Reborn“) — Spross startet neu mit permanentem Gold-Ring und +20 % VP, alle Cosmetics bleiben.

Stimmungs-Zustände = der Ambient-Nudge

Der Clou: Diese Zustände lassen sich komplett aus bereits vorhandenen Stats-Feldern berechnen (thirsty_count, days_overdue, watering_consistency_pct) — kein neues Backend nötig.

health_score aus vorhandenem StatsResponse 
health_score =
    (1 − thirsty_count / max(total_plants, 1))           # Anteil versorgt
  × (1 − min(longest_overdue, 7) / 7)                    # schwerste Überfälligkeit
  × (watering_consistency_pct / 100)                     # 30-Tage-Trend
ZustandBedingungSpross sieht aus…Ambient
Blühend0 durstig, Konsistenz ≥ 80 %leuchtend, Blüte, Glitzer-Pixel, pulsierende AuraHeader leicht golden · „wunderbar.“
Wohl≤1 durstigaufrecht, neutral— (Stille ist auch Aussage)
Durstig2–4 durstigBlätter leicht hängend, blasser, müder Blick, Tropfen-Icon„durstig.“
Welkend≥5 durstig oder 1 Pflanze >7 Tage übergebeugt, entsättigt, Augen fast zu„oh…“ — nie ein Vorwurf
NeugierigApp nach >3 Tagen Pause geöffnetAugen weit auf, Ärmchen ausgestreckt„da bist du.“

Erholung = so schnell wie der Verfall. Gießt du alle überfälligen Pflanzen, richtet sich Spross sofort wieder auf (1,2-s-Animation, kein Konfetti). Kein Straf-Timer, der den User in der Schuld-Zone hält.

Der tägliche Loop — popup-frei

App öffnen → durstige Pflanzen leuchten warm-golden (kein Badge-Alarm)
          → Spross zeigt seinen Zustand (s.o.)
[Gegossen] → Wasserpartikel an der Kachel (400 ms) + Spross-Freudewackeln
          → Fortschrittsbalken füllt sich still

Warum Magenta-Hintergrund?

Jeder Prompt fordert einen flachen Magenta-Hintergrund #FF00FF an — nicht „transparent“. Gemini ignoriert Transparenz oft und malt ein Schachbrett; eine flache Farbe, die im Charakter nicht vorkommt, lässt sich dagegen perfekt wegschneiden. Magenta, weil die Pflanze nur Grün/Braun/Gold/Rosa/Weiß nutzt — Rot würde mit Topf, Wangen und der Beere (Stufe 6) kollidieren. Das Cut-Skript erkennt Magenta automatisch und entfernt sogar den violetten Rand-Spill.

Schritt 3 — Sprite-Sheets bauen

Variante A — automatisch (empfohlen)

Kein Klick-Tool nötig: Das Skript scripts/build_sprites.py (Pillow + numpy) erledigt alles auf einmal — es entfernt den Hintergrund (erkennt die BG-Farbe selbst: helles Schachbrett und farbiger/dunkler BG, beides kommt bei Gemini-Exporten vor), schält den hellen/farbigen Matte-Halo an den Kanten ab, richtet die Frames an der Topf-Grundlinie aus und montiert sie zum Sheet. Augen-Highlights (eingeschlossenes Weiss) bleiben erhalten; ein weicher Glow (z. B. Stufe 6) wird transluzent statt zur opaken Creme-Wolke. Tipp: Ergebnis auf dunklem App-Hintergrund prüfen, nicht auf hellem — ein warmer Glow täuscht sonst.

Schritt 4 — Animationen

Fertig ✓

Alle 6 Stufen-Sheets sind gebaut und liegen in frontend/public/sprites/ (spross-stage1.png … spross-stage6.png — je 1280×256, also 5 Frames à 256×256). Die CSS-Animationen unten laufen direkt auf diesen Sprites — nichts mehr zu generieren.

Das Wichtigste zuerst

Die zentralen Animationen brauchen kein einziges neues Bild — CSS animiert die Sprites, die du schon hast. Das reicht für den MVP. Handgezeichnete Frames (weiter unten, optional) geben mehr Charakter, sind aber das Schwierigste für die KI.

A · Freudewackeln — nach dem Gießen · nur CSS, kein Bild 
@keyframes freude {
  0%,100% { transform: rotate(0deg) scaleY(1); }
  25%     { transform: rotate(6deg) translateY(-3px); }

frontend/src/components/Spross.tsx 
// Sprite-Sheet: 5 Frames nebeneinander — Frame-Reihenfolge fixiert:
// 0 = wohl  1 = blühend  2 = durstig  3 = welkend  4 = neugierig

const FRAME_SIZE = 256; // Quell-Frame im Sheet (build_sprites.py: 256x256). CSS skaliert per width/height.
const MOOD_FRAME = { wohl:0, bluehend:1, durstig:2, welkend:3, neugierig:4 } as const;

const SKIN_FILTER: Record<string, string> = {
  nachtgarten:  'hue-rotate(140deg) saturate(0.65) brightness(0.55)',
  wuestengold:  'hue-rotate(38deg) saturate(1.6) sepia(0.35)',
  steinmoos:    'saturate(0.28) brightness(0.82) contrast(1.1)',
  bluetenweis:  'saturate(0.18) brightness(1.45) contrast(0.9)',
  seelenbluete: 'hue-rotate(260deg) saturate(0.85) brightness(0.9)',
};
const MOOD_FILTER: Record<string, string> = {
  welkend: 'saturate(0.35) brightness(0.85)',
  durstig: 'saturate(0.7)',
};

function spriteFilter(skin?: string, mood?: string) {
  return [MOOD_FILTER[mood ?? ''], SKIN_FILTER[skin ?? '']]
    .filter(Boolean).join(' ') || 'none';
}

type SprossProps = {
  stage: 1 | 2 | 3 | 4 | 5 | 6;
  mood: keyof typeof MOOD_FRAME;
  skin?: string;
};

export function Spross({ stage, mood, skin }: SprossProps) {
  return (
    <div
      style={{
        width: FRAME_SIZE,
        height: FRAME_SIZE,
        backgroundImage: `url('/sprites/spross-stage${stage}.png')`,
        backgroundPosition: `${MOOD_FRAME[mood] * -FRAME_SIZE}px 0`,
        backgroundRepeat: 'no-repeat',
        imageRendering: 'pixelated',   // verhindert Browser-Blur beim Upscaling
        filter: spriteFilter(skin, mood),
      }}
      role="img"
      aria-label={`Spross Stufe ${stage}`}
    />
  );
}

// Verwendung: <Spross stage={2} mood="durstig" skin="nachtgarten" />
