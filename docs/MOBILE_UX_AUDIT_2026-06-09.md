### M3. Falsches 'Kopiert ✓'-Feedback, obwohl der Clipboard-Write gar nicht stattfand  ·  `interaction-feedback`
- **Datei:** `src/pages/SettingsPage.tsx:296-303`
- **Problem:** navigator.clipboard?.writeText(inviteUrl) ist per Optional-Chaining ein No-op, wenn die Clipboard-API fehlt - genau der Fall bei einem selbstgehosteten Pi ueber http://<LAN-IP> (kein secure context), und writeText kann ausserdem rejecten (Permission). Trotzdem laufen setCopied(true) und announce(t('settings.copied')) bedingungslos. Der Nutzer sieht/hoert 'Kopiert ✓', die Zwischenablage ist aber leer - irrefuehrendes Erfolgs-Feedback genau dort, wo es auf Mobil am wahrscheinlichsten fehlschlaegt.
- **Fix:** Das Erfolgs-Feedback an das Promise binden: navigator.clipboard?.writeText(url)?.then(() => {setCopied(true); announce(...)}).catch(...); wenn die API fehlt oder rejected, kein '✓' zeigen, sondern das readonly-Feld selektieren/Hinweis 'lange druecken zum Kopieren' inline anbieten.
- **Verifikation:** Im Code bestaetigt @ SettingsPage.tsx:297-303: navigator.clipboard?.writeText(inviteUrl) ist per Optional-Chaining ein No-op, wenn navigator.clipboard fehlt — genau der Fall bei selbstgehostetem Pi ueber http://<LAN-IP> (kein secure context), ein dokumentierter PlantPal-Hosting-Modus. setCopied(true) und announce(t('settings.copied')) laufen unmittelbar danach bedingungslos; das Promise wird nie .then/.catch-behandelt, also fuehrt auch ein reject (Permission/nicht fokussiert) zu falschem Erfolg + unhandled rejection. Verifiziert: announce() schreibt in eine aria-live=polite-Region (Feedback.tsx:83/126), d.h. auch Screenreader-Nutzer hoeren faelschlich 'Kopiert!'. Kein execCommand-Fallback und keine isSecureContext/Feature-Detection vorhanden (einzige Clipboard-Stellen im src). Auf echtem Handy spuerbar: Nutzer tippt Kopieren, sieht '✓ Kopiert!', Zwischenablage bleibt leer — irrefuehrend im zentralen Invite-Flow. Severity medium statt high, weil der dokumentierte v3-Cloudflare-Deploy HTTPS nutzt (API funktioniert dort) und ein manueller Workaround existiert (readonly-Input selektiert bei Fokus -> langer Druck zum Kopieren); nicht low, weil falsches Erfolgs-Feedback visuell UND fuer Screenreader in einem real dokumentierten HTTP-LAN-Szenario auftritt.
